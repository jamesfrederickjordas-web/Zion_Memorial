1. PROJECT BACKGROUND & PROBLEM STATEMENT
--------------------------------------------------------------------------------
* The Manual Problem:
  Zion Memorial Garden previously operated on physical paper logbooks, manual 
  ledgers, and verbal plot allocations. This caused:
  1. Risk of duplicate plot reservations (double-selling).
  2. Severe delays in plot location during burials and family visits.
  3. Tedious installment (amortization) tracking and calculation errors.
  4. Physical vulnerability of paper records to deterioration and loss.

* The Solution:
  A secure, cloud-enabled Software-as-a-Service (SaaS) web application integrating:
  - Interactive SVG/Canvas cemetery mapping
  - Online self-service reservations
  - Walk-in cashier point-of-sale (POS)
  - Automated financial amortization tracking
  - Centralized deceased interment records & public grave locator


2. SYSTEM ARCHITECTURE & TECH STACK
--------------------------------------------------------------------------------
* Architecture Pattern: 
  3-Tier Web Application (Frontend Client/Admin -> Local State/Event Bus -> Cloud BaaS)

* Frontend:
  - Clean Semantic HTML5
  - CSS3 Custom Properties (Design System with nature-inspired palette)
  - Vanilla ES6+ JavaScript (Zero heavy framework overhead, fast on all devices)

* Backend & Database:
  - Supabase (PostgreSQL 15) providing relational data integrity, Foreign Keys, 
    and Row-Level Security (RLS) policies.
  - Built-in Supabase Auth for JWT session management.

* Mapping Engine:
  - Custom SVG coordinate-mapped canvas layered over high-res aerial boundary
    imagery (assets/images/backgrounds/cemetery-boundary-bg.png).

* Financial & Payment Engine:
  - Pure JavaScript amortization engine calculating Spot Cash and Installments
    (12, 24, 36, and 60 months).
  - Dynamic QR code generator, Base64 image compressor, and printable receipts.


3. CORE DATABASE TABLES & DATA DICTIONARY
--------------------------------------------------------------------------------
1. profiles:
   Extends auth users with personal contact info.
   Key Columns: id (UUID PK), full_name, phone, role ('client', 'staff', 'admin').

2. memorial_spaces:
   Master cemetery plot inventory & coordinates.
   Key Columns: id, plot_identifier, category, section_name, price, down_payment, 
                status ('available', 'reserved', 'occupied', 'maintenance'), 
                map_coordinates.

3. reservations:
   Booking contracts and financial terms.
   Key Columns: id, reservation_number, user_id, space_id, 
                plan_type ('PRE-NEED', 'AT-NEED'), payment_method, 
                installment_term_months, total_price, down_payment_amount, 
                monthly_amortization, total_paid, balance, 
                status ('PENDING', 'APPROVED', 'CANCELLED'), notes.

4. payments:
   Financial transactions and remittances.
   Key Columns: id, reservation_id, payment_reference, amount, 
                payment_type ('DOWN_PAYMENT', 'MONTHLY_INSTALLMENT', 'FULL_PAYMENT'), 
                payment_method, status ('COMPLETED', 'PENDING'), paid_at.

5. payment_schedules:
   Monthly amortization ledger dues.
   Key Columns: id, reservation_id, installment_number, due_date, amount_due, 
                status ('PENDING', 'PAID', 'OVERDUE').

6. memorial_records:
   Deceased interment details & grave index.
   Key Columns: id, space_id, family_contact_id, deceased_name, birth_date, 
                death_date, burial_date, gender ('Male', 'Female', 'Other'), 
                epitaph, memorial_photo_url.

7. system_settings:
   Dynamic cloud portal settings.
   Key Columns: key (TEXT PK), value (JSONB), description, updated_at, updated_by.
   Example key: 'gcash_qr_config' (Stores Base64 QR image, merchant name & mobile).

8. audit_logs:
   Immutable system event trail.
   Key Columns: id, admin_user_id, action_type, table_name, record_id, details, 
                created_at.


4. CRITICAL BUSINESS LOGIC (KEY RULES FOR DEFENSE)
--------------------------------------------------------------------------------
A. Pre-Need vs. At-Need Plan Types:
   - Pre-Need: Acquired in advance as estate planning or future family investment.
     Deceased details are OPTIONAL upon reservation and can be assigned later.
     Plot status is set to 'reserved'.
   - At-Need: Acquired for an immediate death and interment.
     Deceased First Name, Last Name, and Date of Burial are MANDATORY.
     A record is immediately generated in memorial_records and plot status is 
     set to 'occupied'.

B. Online Portal vs. Admin Walk-In Reservation:
   - Online Portal: Customer is already logged in with an authenticated account.
     Customer selects GCash QR, Maya, Bank, or Cash. Status begins as 'PENDING'.
   - Admin Walk-In Form: Physical customer is at the office counter. Cashier inputs 
     client contact details, takes cash, immediately approves the booking ('APPROVED'), 
     and prints an official cash receipt.

C. Dynamic GCash QR Gateway:
   - Admin uploads custom QR in Admin Setup.
   - Compressed client-side via HTML5 Canvas into Base64 and saved in system_settings.
   - Syncs in real time via DOM events, cached in localStorage, with static SVG fallback.

1. Built dynamic GCash manager supporting custom QR uploads with canvas compression.

1. Indexed memorial_records to power fast name searching.
2. Displays deceased dates, plot location, and epitaph for park visitors.

PART 3: TOP DEFENSE QUESTIONS & ANSWERS (Q&A CHEAT SHEET)
================================================================================

Q1: Why use Supabase instead of traditional MySQL with PHP?
A1: Supabase provides enterprise PostgreSQL with built-in JWT authentication, 
    Row-Level Security (RLS) directly inside the database engine, and instant 
    RESTful APIs. This eliminates massive backend boilerplate code while 
    guaranteeing tighter security.

Q2: How does the system prevent double-selling of plots?
A2: Atomic database transactions and SQL status checks verify that space_id has 
    status = 'available' before committing the reservation row.

Q3: What is the difference between Pre-Need and At-Need in the database?
A3: At-Need strictly requires Deceased First Name, Last Name, and Date of Burial, 
    inserting an immediate record into memorial_records and updating the space to 
    'occupied'. Pre-Need allows deceased fields to be null/empty, setting the 
    space to 'reserved'.

Q4: Where is the GCash QR code stored?
A4: Stored in the Supabase table public.system_settings under key 'gcash_qr_config' 
    as JSONB holding a compressed Base64 data URL. It is cached in browser 
    localStorage and defaults to assets/images/gcash-qr-default.svg if unconfigured.
